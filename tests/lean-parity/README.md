# lean parity: PyTorch-trained LoRA vs. llm-web's `lean` engine

This directory holds the artifacts from checking that a LoRA adapter
trained from scratch by this branch's PyTorch port — not a natively
Burn-trained one — loads in llm-web's `lean` inference engine and produces
matching logits.

- `lora_parity_pytorch.rs` — a Rust test for `llm-web`'s `crates/lean`,
  a copy of `lora_and_sliced_head_match_reference` in
  `crates/lean/tests/lora_parity.rs` pointed at `fixture_lora_pytorch.json`
  instead of the published-adapter fixture. Not part of this repo's own
  test suite (it depends on `lean`'s crate, which lives in `llm-web`); kept
  here only so the artifact isn't lost, since it was never committed to
  `llm-web`.
- `fixture_lora_pytorch.json` — the reference logits, generated by
  `llm-web`'s `crates/lean/reference/gen_fixture_lora.py` (transformers'
  own GGUF-loaded base plus hand-applied LoRA deltas via forward hooks) run
  against `lora-b-16-s3-300-pytorch-LLMLIFE2.bin` — this branch's PyTorch
  retrain of the published `lora-b-16-s3-300` adapter (see
  `docs/runs/2026-09-29-pytorch-retrain.md`), converted from PEFT-layout
  safetensors to `LLMLIFE2` with `tools export --import-lora` (see
  `docs/pytorch-training.md`).

## How to rerun this against llm-web

1. In an `llm-web` checkout with `crates/lean` (a `lean-perf` branch or
   later, whichever has `apply_lora`/`lm_head_sliced`/`ForwardSpec`):
   ```bash
   cp tests/lean-parity/lora_parity_pytorch.rs  <llm-web>/crates/lean/tests/
   cp tests/lean-parity/fixture_lora_pytorch.json <llm-web>/crates/lean/reference/
   ```
2. Convert a PyTorch-trained adapter (a `.safetensors` this branch's
   `pytorch/train_variant_{a,b}.py` wrote) to `LLMLIFE2`:
   ```bash
   cargo run --release -p llm-life --bin export --no-default-features \
     --features native,cpu,export -- \
     --import-lora <adapter>.safetensors --rank 8 --alpha 16 \
     --out <adapter>-LLMLIFE2.bin
   ```
3. Run the test (needs a GPU-backed `wgpu` adapter; on a shared machine,
   run it under whatever GPU lock that machine's convention uses):
   ```bash
   LEAN_GGUF=<qwen2.5-0.5b-instruct-q4_0.gguf> \
   LEAN_LORA_BIN=<adapter>-LLMLIFE2.bin \
   cargo test -p lean --release -- --ignored pytorch_trained_lora_matches_reference --nocapture
   ```

If the adapter being checked is different from the one `fixture_lora_pytorch.json`
was generated against, regenerate the fixture first with
`gen_fixture_lora.py` (`LEAN_GGUF`, `LEAN_TOKENIZER_DIR`, `LEAN_LORA_BIN`
env vars — see that script's own doc comment) before running step 3.

## Result (2026-09-29, RTX 3080 box, Vulkan backend)

```
[lora_parity_pytorch] base:  dead=22.063770 alive=23.350809 (fixture dead=22.063786 alive=23.350847)
[lora_parity_pytorch] +lora: dead=22.415054 alive=21.142834 (fixture dead=22.415058 alive=21.142822)
test pytorch_trained_lora_matches_reference ... ok
```

Max abs diff ~1.6e-5 (base) / ~1.2e-5 (+LoRA), well inside the existing
test's 2e-2 tolerance (the tolerance exists for the gap between `lean`'s
own Q4_0 GPU dequant kernel and transformers' GGUF dequant-on-load, two
independent implementations of the same block math). This is the load-
bearing result: a PyTorch-trained-from-scratch adapter, converted to
`LLMLIFE2`, runs correctly in `lean`'s actual WGSL forward pass.
