# Merging variant-A LoRA adapters into GGUF for the browser engine

Offline merge of the trained variant-A LoRA adapters
(`artifacts/lora-a-{norules,rules}-300.bin`, rank 8, alpha 16, q/k/v/o only —
see `docs/runs/2026-09-20-ft-a-norules-300.md` /
`2026-09-20-ft-a-rules-300.md`) into the base Qwen2.5-0.5B-Instruct GGUF, so
llm-wasm can load a fine-tuned model exactly like any other GGUF. llm-wasm's
LoRA-free forward has no adapter path, so this has to happen offline and the
result re-exported as a plain GGUF.

Tooling: `tools/merge/` (venv `tools/merge/.venv`, gitignored — `python3 -m
venv .venv`, then `pip install numpy gguf` and `pip install torch
--index-url https://download.pytorch.org/whl/cpu`). CPU only throughout, no
GPU use on this machine.

## Method

**Base precision.** No safetensors/bf16 copy of Qwen2.5-0.5B-Instruct exists
under `models/hf/` on this machine — only `config.json`/`tokenizer.json`.
The only weights available are the Q4_0 GGUF
(`models/gguf/Qwen2.5-0.5B-Instruct-GGUF/qwen2.5-0.5b-instruct-q4_0.gguf`),
so that is the highest-precision base actually available, and the merge
dequantizes it to f32 rather than merging into a higher-precision source.
This matters for the Q8_0 output: it cannot recover precision Q4_0 already
discarded, it only avoids adding *further* rounding at merge/requantize
time (see "Delta survival" below).

**Merge math** (`tools/merge/merge_lora_gguf.py`, matched against
`crates/llm-life/src/train/model.rs` `Lora::delta`/`TrainLinear::forward` and
`crates/llm-life/src/train/weights.rs`'s layout note):
- `TrainModel` weights are `[in_features, out_features]` (GGUF/`Q4Linear` are
  `[out_features, in_features]`, transposed once at load).
- `delta(x) = (x @ a) @ b * (alpha / rank)`, `a: [in, rank]`, `b: [rank,
  out]`, added to `x @ w`. So in TrainModel layout `w' = w + scale * (a @
  b)`, `scale = alpha/rank`.
- Transposed back to GGUF's `[out, in]`: `W' = W + scale * b^T @ a^T`.
- Adapted projections (`crates/llm-life/src/train/load.rs::build`): `q, k,
  v, o` always; `gate, up` iff the adapter's `LoraSpec.mlp` is set (false for
  both `-300` adapters — q/k/v/o only); `down` is never adapted.

**Tensor names / metadata** (unchanged from the base file, ggml/llama.cpp
convention, what `crates/llm-wasm/src/gguf.rs` reads): `blk.{i}.attn_{q,k,v,
output}.weight` (+ `attn_{q,k,v}.bias`), `blk.{i}.ffn_{gate,up,down}.weight`,
`blk.{i}.{attn,ffn}_norm.weight`, `output_norm.weight`,
`token_embd.weight`. `merge_lora_gguf.py` copies every KV metadata field and
every non-adapted tensor byte-for-byte from the base file (including an
unused `output.weight` Q8_0 tensor some base GGUFs ship alongside the tied
embedding), and only replaces the adapted linears' bytes.

**Command** (run for each of the two adapters):
```
python3 tools/merge/merge_lora_gguf.py \
  --base models/gguf/Qwen2.5-0.5B-Instruct-GGUF/qwen2.5-0.5b-instruct-q4_0.gguf \
  --adapter artifacts/lora-a-norules-300.bin \
  --out-prefix artifacts/qwen2.5-0.5b-life-a-norules
# and the same with lora-a-rules-300.bin / -a-rules out-prefix
```

Each run writes two whole-model requantizations, not "Q4_0 everywhere except
a few merged tensors": every `q/k/v/o/gate/up/down` projection across all 24
layers is dequantized (merged where adapted, passed through unchanged
otherwise) and requantized into the target format, using a numpy Q4_0/Q8_0
quantizer (`tools/merge/ggml_quant.py`) matched to llama.cpp's reference
quantizer and to `crates/llm-life/src/train/weights.rs`'s dequantizer
byte-for-byte (verified: dequantizing then requantizing the base file's own
`blk.0.attn_q.weight` reproduces its exact original bytes). Norms, biases,
`token_embd.weight` and the unused `output.weight` are left untouched.

(`artifacts/` is gitignored; these are local only.)

**Loadability caveat — read before pointing the web page at the Q8_0
file.** `crates/llm-wasm/src/gguf.rs`'s `Q4ModelLoader::load_q4_linear` /
`load_q4_linear_with_bias` hard-require `GgmlDtype::Q4_0` for every
`attn_{q,k,v,output}`/`ffn_{gate,up,down}` tensor and `bail!` otherwise
("Expected Q4_0 for '...', got Q8_0"). Q8_0 is only accepted for
`token_embd.weight` (`EmbeddingStore`). So **only the `-q4_0.gguf` files load
in the current browser engine**; the `-q8_0.gguf` files are offline
accuracy references only, useful for judging how much of the accuracy loss
below is from the fine-tune surviving 4-bit rounding vs. from the merge
itself. This is a property of the existing loader, not something this task
changed — no `crates/` edits were made or needed.

## Verification

**1. Numerical merge check without a GPU.** No CPU/ndarray backend exists in
this crate (only `Autodiff<Wgpu>`, which on this Mac means Metal), and the
task constraint is no GPU use on this laptop, so the Rust training/inference
binaries were not run at all — not even for a reference number. Two checks
were done entirely in Python instead:

- `tools/merge/verify_delta.py` reloads each merged GGUF, dequantizes the 96
  adapted tensors (24 layers x q/k/v/o), and compares them against an
  independently recomputed f32 merge (base dequant + `scale * b^T @ a^T`,
  not reusing `merge_lora_gguf.py`'s own arrays):

  | file | requant error vs f32 merge (mean / max) | delta survival (mean / min / max) |
  |---|---|---|
  | norules-q4_0 | 3.93% / 7.10% | 0.73 / 0.35 / 1.03 |
  | norules-q8_0 | 0.63% / 0.91% | 1.02 / 1.00 / 1.13 |
  | rules-q4_0 | 4.15% / 7.52% | 0.75 / 0.32 / 1.08 |
  | rules-q8_0 | 0.63% / 0.91% | 1.01 / 1.00 / 1.11 |

  "Requant error" is the ordinary weight-quantization error of the *merged*
  tensor against its exact f32 value — this is the number the task's "Q8
  should be < 1%, Q4 a few %" bar is about, and it lands where expected.
  "Delta survival" (`||dequant(merged_q) - dequant(base_q)|| / ||scale * b^T
  a^T||`) is a secondary, noisier diagnostic: the LoRA delta itself is only
  ~5-10% of `||W||` (`merge_lora_gguf.py` prints this per run — up to 8.65%
  for norules, 9.57% for rules, both on `blk.0.attn_v.weight`), which is
  comparable to one Q4_0 quantization step, so Q4_0 visibly attenuates the
  fine-tuned signal (mean survival 0.73-0.75) while Q8_0 preserves it almost
  exactly (mean 1.01-1.02). Low delta-survival at Q4_0 is expected, not a
  bug — it is exactly the risk of merging into a 4-bit base instead of a
  higher-precision one, and it is why the functional check below (not just
  the tensor-level check) is the one that matters.

- A from-scratch Qwen2 forward in Python/torch, CPU, f32
  (`tools/merge/qwen2_forward.py`, matched piece-by-piece to `TrainModel`:
  RMSNorm, rotate-half RoPE, GQA with q/k/v bias, SwiGLU, tied-embedding
  head sliced to the two answer tokens), reading weights straight out of a
  GGUF via `gguf.GGUFReader` + the same `ggml_quant.py` dequantizer. Per
  case this reimplements exactly what `run_a.rs::full_sequence`'s
  block-diagonal mask gives a single case: plain causal attention over
  `[prefix, that case's suffix]`, with the packing being purely a batching
  trick, not a change in what any case attends to — so scoring the 512
  cases one sequence at a time is not an approximation of the training
  loop's evaluation, it is the same computation.

  Aside: the "Base (step 0)" line in `docs/runs/2026-09-20-ft-a-rules-300.md`
  reads "accuracy 0.2734 (140/512)" but its own case table sums to 128, not
  512 (`35 + 93`), and `0.2734 * 128 ≈ 35`, matching the table — the `512`
  in that one line looks like a stale label from before the "fix run-doc
  denominators" commit (`d16526f`), not an actual full-512 evaluation. This
  script therefore does **not** try to reproduce that line; it targets the
  full, self-consistent 512-case numbers instead (the "Best-by-accuracy
  checkpoint" section, which does sum to 512 and is what "the adapter's
  512/512" in the merge task refers to).

**2. Functional check: all 512 cases, merged model vs. the adapter's own
number.**

| file | prefix | accuracy | adapter's own (best checkpoint) |
|---|---|---|---|
| norules-q8_0.gguf | norules | 511/512 = 0.9980 | 512/512 = 1.0000 |
| norules-q4_0.gguf | norules | 459/512 = 0.8965 | 512/512 = 1.0000 |
| rules-q8_0.gguf | rules | 509/512 = 0.9941 | 509/512 = 0.9941 |
| rules-q4_0.gguf | rules | 423/512 = 0.8262 | 509/512 = 0.9941 |

Commands:
```
python3 tools/merge/eval_512.py --gguf artifacts/qwen2.5-0.5b-life-a-norules-q8_0.gguf \
  --tokenizer models/hf/Qwen2.5-0.5B-Instruct/tokenizer.json --norules
python3 tools/merge/eval_512.py --gguf artifacts/qwen2.5-0.5b-life-a-rules-q4_0.gguf \
  --tokenizer models/hf/Qwen2.5-0.5B-Instruct/tokenizer.json
# (drop --norules for the a-rules files)
```

The rules-q8_0 number (509/512) is an exact match to the adapter's own
recorded accuracy — strong evidence the merge formula, scaling, target
matrices and transposition convention are all correct end-to-end (any error
in any of those, on a task this close to a lookup table, would show up as a
much larger drop, not a same-to-the-case-count match). norules-q8_0 loses
one case (511/512) to Q8_0 rounding. Both `-q4_0.gguf` files show the
accuracy hit the delta-survival numbers above predicted: real but partial
degradation (89.7% / 82.6%), not a broken merge — a rank-8 LoRA delta that
is only ~5-10% of the weight norm sits close to Q4_0's own quantization
step, so some of what training changed gets rounded away. All 512 cases
were run for both files (no need to fall back to the 64-case subset the
task allowed for).

Grid-level IoU (the training run's other metric, on 16x16 glider/blinker/
random grids) was not independently re-run: variant A's per-cell prompts
are architecturally independent (block-diagonal masking, no cross-cell
attention), so the model's answer for a grid cell depends only on that
cell's neighbor pattern — exactly the 512-entry table already scored above.
512/512 or 509/512 case accuracy therefore implies the same IoU the training
run recorded (1.0000 / 0.9909) by construction, not by assumption specific
to this merge.

## Practical takeaway for the browser demo

Use `qwen2.5-0.5b-life-a-norules-q4_0.gguf` or
`qwen2.5-0.5b-life-a-rules-q4_0.gguf` — these are the only merged files the
current llm-wasm loader accepts, and their accuracy loss from LoRA-into-Q4_0
merging (to 89.7% / 82.6% on the full 512-case table) is real and larger
than "a few %"; if that's not acceptable for the demo, the fix is upstream
of this script (e.g. teach `Q4ModelLoader` to accept Q8_0 linears, or find/
produce a higher-precision base to merge into before quantizing) — both are
`crates/` changes and out of this task's scope.
