# Variant A LoRA fine-tune — smoke test (a-rules), before the real runs

Not the deliverable run. This is the smoke test that caught and confirmed
the fix for a real bug in the training loop, kept as the paper trail before
`docs/runs/2026-09-19-ft-a-rules.md` / `...-ft-a-norules.md`.

machine: Apple M2, macOS (Darwin 25.3.0 arm64), Metal via Burn 0.20 / wgpu.
llm-life commit: `732fc63` (pre-CHUNK=128 bump).
GPU otherwise idle (`ps -A -o comm | grep -E 'target/release/(jacobi|llm-life)'` empty at launch).

command:

```
./target/release/llm-life train-a \
  --gguf .../Qwen2.5-0.5B-Instruct-GGUF/qwen2.5-0.5b-instruct-q4_0.gguf \
  --tokenizer .../Qwen2.5-0.5B-Instruct/tokenizer.json \
  --steps 3 --batch 32 --eval-every 1 --max-secs 180 --out /tmp/lora-a-smoke.bin
```

## The bug

`evaluate_a`'s eval loop (40 forwards — 16 case-chunks of 32 plus 3 real
grids at 8 chunks of 32 each) runs entirely before the training loop's first
`backward()`. Burn's autodiff backend keeps every forward's graph nodes
alive until something walks and consumes them; with none of these forwards
ever backed-propagated, the tape grows without bound. `/usr/bin/time -l`
measured **69-70GB peak memory footprint** (RSS only ~500MB — this is
committed/mapped GPU-buffer space, the metric macOS's jetsam OOM killer acts
on) after ~40 forwards at CHUNK=32, killed with SIGKILL (exit 137) before
printing the first eval result, reproduced twice (also at CHUNK=128 before
the chunking-by-cell fix for the real-grid loop was in place).

**Fix**: a throwaway `.backward()` (and `drop()` of the resulting
`Gradients`) after every eval-loop forward. These gradients are never read —
`AdamW::step` takes its own explicit `Gradients` object per real training
step, so there is no interference with the actual optimization — but calling
`backward()` is what releases Burn's retained graph.

## Result (1 step, `--max-secs 180` reached during the second eval)

| step | loss | accuracy | n correct | IoU (3 real grids) |
|---|---|---|---|---|
| 0 (base) | 0.9874 | 0.4199 | 215/512 | 0.0554 |
| 1 | held-out: 0.5773 | 0.7266 | 372/512 | 0.0000 |

Training step itself: 13.6s. Peak memory footprint after the fix: **9.3GB**
(down from 69-70GB), real time 1126s dominated by two full 40-forward evals
(before + step-1) at CHUNK=32 — an eval this size at ~14s/forward (forward +
throwaway backward) is far too slow for a 15-minute budget across many
`eval-every` checkpoints, so the real runs bump `CHUNK` to 128 (fewer,
larger forwards) before launching.

Not a claim about the adapter: one step, no norules run, not the deliverable.

## Diagnosis of the second smoke (CHUNK=48, `--batch 64`, appeared stuck 8+ min)

`sample $(pgrep -f 'llm-life train-a') 5 -file /tmp/ft-a-sample.txt` while it
looked idle: **not a hang.** The hot stack is
`burn_autodiff::graph::Step::step -> burn_cubecl::…::float_matmul ->
cubecl_runtime::tune::FunctionTunable::execute -> launch_matmul ->
WgpuServer::launch -> WgpuStream::flush -> Device::poll/wait` — a real
Metal dispatch inside cubecl's kernel **autotune** (12/2195 sampled frames in
`Tune*`, 35/2195 in matmul launch), one GPU sync per candidate kernel. It
finished on its own: killed right as it printed
`step 1 loss 0.9743  32.8s`, i.e. `step 0 (base)` (the unconditional 512-case
+ 3-grid eval, 29 forwards at CHUNK=48 — plus two ragged remainder chunks,
512%48=32 and 256%48=16, each a distinct shape needing its own autotune pass)
took **~8-9 minutes** on its own, unbounded by `--max-secs` (that check only
runs inside the training loop, after `before` is computed).

One-line fix does not exist here: the real problem is that evaluating a
29-forward, mostly-backward-flushed pass before every run (and again for
early-stop checks) does not fit a 15-minute wall-clock budget at this
CHUNK/shape count, autotune warmup or not. `--batch 64` also does not match
`CHUNK=48`, so the training step itself pays a second cold autotune the
before-eval didn't already warm.

Handed back to the lead per instruction rather than attempting a third
CHUNK-size guess.

## Smoke 3 — CHUNK unified with `--batch`, padded remainders, `--eval-cases`/`--eval-grids`, wall-clock-aware eval loop

Fix for the diagnosis above: `evaluate_a` now takes `chunk_size` (set to
`--batch`, so eval and training forwards share exactly one shape — cubecl's
matmul autotune fires once for the whole run, not once per distinct ragged
remainder shape), pads every ragged remainder up to a full chunk by
repeating a real case/cell (masked out of loss/accuracy/IoU accounting via
an explicit `real_len`/`done` count, never counted twice), and checks
`start.elapsed() > max_secs` between every chunk in both the case loop and
the per-grid cell loop, returning a `partial: bool` report instead of
running unbounded. `--eval-cases` (default 128) and `--eval-grids` (default
1) shrink the before-training and periodic evals; the final (`--run-doc`)
eval still uses all 512 cases and all 3 real grids, on its own fresh
wall-clock window (not the training loop's already-spent budget). Step 1's
log line is suffixed `(includes autotune)`. `stdout` is flushed after every
step and eval line.

machine: Apple M2, macOS (Darwin 25.3.0 arm64), Metal via Burn 0.20 / wgpu.
GPU otherwise idle (`pgrep -f 'jacobi|t0|llm-life'` checked clear immediately
before launch; a concurrent `cargo test -p jacobi2000` on the same box was
allowed to finish first).

command:

```
./target/release/llm-life train-a \
  --gguf .../Qwen2.5-0.5B-Instruct-GGUF/qwen2.5-0.5b-instruct-q4_0.gguf \
  --tokenizer .../Qwen2.5-0.5B-Instruct/tokenizer.json \
  --steps 5 --eval-every 5 --batch 64 --max-secs 600 --out /tmp/lora-a-smoke3.bin
```

First attempt at the instructed `--max-secs 240` produced only the step-0
eval (128 cases + 1 grid, one chunk shape, one autotune) before the
wall-clock check tripped at the top of the training loop: the one-time
matmul autotune for this T alone costs ~230-280s on this GPU, independent of
how many forwards share the shape (cubecl benchmarks each candidate kernel
with a real dispatch + sync, and that per-candidate cost, not forward count,
dominates). That is exactly the bug this fix targets — one autotune instead
of three — but 240s is not enough headroom on this hardware for a 5-step
smoke to clear the autotune *and* run training; bumped to 600s to observe
the rest of the loop.

Confirms: exactly one autotune for the whole run (step 1's ~48s training
step, minus steps 2-5's ~40-49s each, shows no second cold-start spike);
padded ragged remainders never double-count (128/128 cases correct
denominator both at step 0 and held-out); the held-out eval's IoU pass hit
the 600s ceiling on its first grid chunk and correctly reported `partial`
(iou 0.0000, the empty-average default) rather than hanging or lying about
a completed pass. Per-step time (~40-50s at batch 64, warm) is still far
from the 13.6s/step at batch 32 noted in the first smoke — batch doubled,
and this GPU is now also carrying the single amortized chunk shape for both
eval and train, so the real 300-step runs need a wall-clock budget sized off
this number (steps 1-4 solo: ~40-49s/step -> ~300 real steps in ~2.5-3.5h),
not the `900s`/`--max-secs 900` figured from the old per-step numbers.
