## Anomaly: IoU vs true Life in the browser does not match the native rollout — flagging, not fixing

`docs/runs/2026-09-20-a-rollout.md` reports **IoU 1.0000** for a-norules,
seed 1, density 0.28, 16², generation 1 (native f32 forward path, 3080).
The identical seed through this repo's browser/WebGPU runtime-LoRA path
(`LifeEngine::loadAdapter` → `Q4Attention::lora`, Metal backend via
Chromium's WebGPU) gave:

```
generation 1: 39.5 s · threshold otsu 0.258 · live 100 (game of life 83) · acc 0.621 · IoU 0.307 · wrong 97
```

Reproduction:
```
node scripts/headless/llm-narrated.mjs
# or: node scripts/headless/llm.mjs --mode llm-a --seed random --generations 1
```
Both scripts (the new narrated one and the pre-existing `llm.mjs`, whose
per-cell/chunking code this task did not touch) reproduce the same
acc≈61–62%, IoU≈0.30–0.31, `live≈100` vs `true_live=83` on this seed — so
this is not something the narration/adapter-toggle UI work introduced; it
reproduces on the unmodified engine/worker step path (`LifeEngine::step_chunk_a`).
`docs/runs/2026-09-20-runtime-lora.md` verified the runtime LoRA path exactly
matches training-time accuracy (512/512 on the exhaustive lookup, 16×16 IoU
1.0000) via `lora_eval` — but that check runs **native** (Vulkan, the 3080),
not through a browser WebGPU/Metal backend. This looks like a
browser/Metal-specific numerical divergence in the runtime LoRA forward
path (base Q4 + f32 LoRA delta) that the native-only verification didn't
cover. Per this agent's scope (browser glue, not WASM/kernel internals) —
reporting for hand-off, not debugging further.

The sparse `glider` seed (5 live cells) gave an even more IoU-sensitive
result (IoU 0.50, only 4 wrong cells out of 256) purely from the small
union — not by itself evidence of the same bug, but consistent with it.
