# bert-text: a from-scratch text encoder reading the LLM's own prompt

What was copied before writing any code:

- **"BERT of Life" architecture and training setup**: `crates/llm-life/src/bert/model.rs`
  (`BertOfLife`: a token embedding over the 9 neighbourhood cells as 0/1
  tokens + a learned position embedding, a plain transformer encoder, a
  2-class linear head reading the centre/CLS token) and `crates/llm-life/src/bert/data.rs`
  (the exhaustive 512-case indexing: 8 neighbour bits then the cell's own
  state as bit 8). The run doc `docs/runs/2026-09-20-bert.md` is the source
  for the smallest-exact-model numbers quoted below (BERT d=16 L=1 H=1,
  3,490 parameters, exact on 512 in 105 steps at lr=2e-3).
- **The LLM per-cell prompt format**: `crates/llm-life/src/variant_a.rs`
  `cell_prompt()` ("Neighbors: n0 n1 ... n7 / Self: s / Next: ", trailing
  space kept) and `norules_prefix()` ("For each cell, answer with one
  digit: its next state.\n") — the `a-norules` adapter's prefix, named
  "the norules format" throughout `docs/runs/2026-09-20-eval-a-base-norules.md`
  and related docs. `rules_prefix()` was read but not reused (variant 2
  below invents its own, shorter "Rule: B3/S23\n" prefix instead — see
  "Design choices").
- The outer-totalistic rule representation (`Rule::parse`/`to_rulestring`,
  `crates/life/src/rule.rs`) is reimplemented in Python in `pytorch/bert_text/prompts.py`
  rather than called via FFI, since the task needed a Python-side rule mixture.

Nothing from `pytorch/qwen_life.py` (the Qwen+LoRA port on the
`pytorch-training` branch) was reused — this is a small encoder trained
from scratch, not a fine-tune of the 0.5B model.

## Context: why this experiment

TC's framing: this is the missing link between the LLM reading text (4,096
separate language-model calls, one per cell, `docs/runs/2026-09-20-a-rollout.md`)
and the tiny from-scratch models reading numbers directly (`bert::model::BertOfLife`,
3,490 params, exact on 512). Here the *input* is still text — the LLM's own
per-cell prompt string, tokenized with the LLM's own tokenizer — but the
*architecture* is the tiny non-autoregressive encoder: one forward pass,
read the CLS token, done. No sampling, no generation loop.

This is the shape described for "Jev" (TypeSafe AI, September 2026):
non-autoregressive, text in, a typed decision with calibrated probabilities
out, in one pass. Noted here as context only — nothing from that project
was read or reused; the architecture here is the repo's own BERT-of-Life
encoder reading text instead of 9 raw bits.

Reference for the encoder-classifier shape: Devlin, Chang, Lee, Toutanova,
"BERT: Pre-training of Deep Bidirectional Transformers for Language
Understanding", arXiv:1810.04805 (2018) — encoder-only, bidirectional
attention, classification from a CLS token, the shape `BertOfLife` already
used and this task extends to text input.

## Design choices (not fully pinned by the brief, stated explicitly)

- **Variant 1 input** = `norules_prefix() + cell_prompt(neighbors, self)`,
  exactly the text fed to the repo's `a-norules` LoRA adapter for one cell
  (minus the multi-cell packing — each of the 512 cases is tokenized and
  classified independently here, batch size 512, no packed attention mask).
- **Variant 2 input** = `f"Rule: {rulestring}\n" + cell_prompt(neighbors, self)`.
  The repo's own `rules_prefix()` spells the rule out in English sentences
  ("A live cell with 2 or 3 live neighbors stays 1..."); this task asked
  for the rule "in B/S notation", so variant 2 uses a new, shorter prefix
  instead of `rules_prefix()` — the English-rules prefix was read, not
  reused, because it doesn't match the brief's B/S-notation requirement.
- **CLS token**: a dedicated `[CLS]` id is prepended to every tokenized
  prompt (not reusing `BertOfLife`'s "read the last token" convention,
  since text prompts here have variable informative content before the
  final `: `); the classifier head reads the CLS position's output.
- **Tokenizer**: Qwen2.5-0.5B-Instruct's own `tokenizer.json` (downloaded
  with `hf download` into the repo's models directory, the same file the
  LoRA adapters in this repo were fine-tuned against), loaded with the
  `tokenizers` library directly (not `transformers`). Path is read from
  `QWEN_TOKENIZER_PATH` (`pytorch/bert_text/vocab.py`), not hardcoded.

## Tokenizer vocabulary reduction

The full tokenizer has 151,665 defined vocab entries; the model's own
`config.json` reserves 151,936 embedding rows (`vocab_size`, padded for
alignment — 271 unused rows). A dense `nn.Embedding(151936, d_model)` at
even `d_model=16` would cost **2,430,976 parameters** just for the token
embedding — roughly 560x the entire smallest exact variant-1 model
(4,338 params total, see below).

Both variants instead scan their own training prompts, tokenize with the
full Qwen tokenizer, collect the set of ids that actually occur, and remap
`sorted(used_ids) -> 3..`, reserving ids `0,1,2` for `PAD`, `CLS`, `UNK`:

| variant | base tokens used | V (incl. PAD/CLS/UNK) | full-vocab embedding cost (d=16) | reduced embedding cost (d=16) |
|---|---|---|---|---|
| 1 (norules, 512 Conway prompts) | 20 | 23 | 2,430,976 | 368 |
| 2 (13 training rules x 512) | 19 | 22 | 2,430,976 | 352 |

(embedding cost = `V * d_model`; both variants happen to need almost the
same vocabulary because the per-cell text dominates each prompt — only the
"Rule: B.../S...\n" prefix adds a handful of extra tokens in variant 2:
`Rule`, `:`, `ĠB`, `/S`, `Ċ`, plus digit tokens, see below.)

Held-out-rule prompts in variant 2 produced **zero** out-of-vocabulary
(UNK) tokens against the variant-2 training vocabulary — every digit
0-8 and every structural token needed by any B/S rulestring already
appears somewhere in the 13-rule training mixture (`n_unk_tokens_in_held_prompts: 0`
in `results_v2.json`).

**Digit tokenization note**: Qwen2.5's tokenizer splits multi-digit
rulestrings into one token per digit — `"B3678/S012345678"` tokenizes as
`['ĠB','3','6','7','8','/S','0','1','2','3','4','5','6','7','8']`, i.e. the
birth/survive digit lists are *not* merged into multi-character number
tokens the way a plain integer like "3678" might be elsewhere in Qwen's
BPE merges. This is convenient for the reduced vocab (only 10 digit tokens
`0`-`9` total ever needed, regardless of how many rules are in the mixture)
and plausibly convenient for the model (each birth/survive digit is a
separate attendable token, not a opaque multi-digit chunk).

## Variant 1: "no rules, Conway only"

Conway (B3/S23) labels. Trained full-batch (all 512 examples per step),
Adam, lr=2e-3, up to 600 steps, 10 seeds per configuration. Encoder: from
scratch (manual multi-head attention, `pytorch/bert_text/model.py`), post-LN,

Sweep wall clock: 1,235.9 s (CPU, Mac, 180 runs: 18 configs x 10 seeds).

**Smallest configuration exact on all 512 cells in all 10 seeds: d_model=16,
layers=1, heads=4, 4,338 parameters** (median 121 steps to exact; the
same `d=16, heads=1` point only reached 9/10 seeds in this budget, so
heads=4 is reported as the reliable smallest point, not heads=1). This is
the same `d=16, layers=1` point `docs/runs/2026-09-20-bert.md` found exact
at 3,490 params reading raw 0/1 bits directly; reading the LLM's own text
prompt through a reduced-vocabulary embedding instead costs 4,338 params
(+848, from `V=23` token-embedding rows vs `BertOfLife`'s `V=2`, plus a
separate position embedding sized for the longer 41-token sequence instead
of 9) for the same exact-on-512 result. Heads 1-4 and layers 1-2 all reach
exactness at this parameter count range; head count does not change the
parameter count (q/k/v/o projections stay `d_model x d_model` regardless
of how many heads split them), so the sweep's variation across head count
is purely a convergence-speed/reliability effect, not a size effect.

## Variant 2: "rule written in the prompt"

**Training mixture** (13 rules x 512 cases = 6,656 examples): Conway
(B3/S23), HighLife (B36/S23), Seeds (B2/S), Day & Night (B3678/S34678),
Life without death (B3/S012345678), plus 8 random outer-totalistic rules
(seed 12345: `B134578/S246`, `B13456/S156`, `B27/S0378`, `B23567/S05`,
`B026/S12456`, `B0136/S35678`, `B2568/S1245`, `B1378/S16`).

**Held-out rules** (never seen in training, 7 rules x 512 = 3,584
examples): 2x2 (B36/S125), Maze (B3/S12345), plus 5 random rules (seed 999,
checked disjoint from the training random set): `B157/S1347`,
`B13458/S18`, `B3468/S1478`, `B134/S0678`, `B14/S0135`.

Trained full-batch, Adam, lr=1e-3, up to 800 steps (checked every 100
steps), 2 sizes x 2 seeds:

| d_model | layers | heads | seed | steps run | params | train rules exact (of 13) | held cells correct | held rules exact (of 7) |
|---|---|---|---|---|---|---|---|---|
| 32 | 2 | 4 | 1 | 700 | 27,554 | 13/13 | 0.5421 | 0/7 |
| 32 | 2 | 4 | 2 | 800 | 27,554 | 0/13 | 0.4590 | 0/7 |
| 64 | 2 | 4 | 1 | 800 | 104,258 | 13/13 | 0.5505 | 0/7 |
| 64 | 2 | 4 | 2 | 800 | 104,258 | 12/13 | 0.5195 | 0/7 |

Full per-rule breakdown: `pytorch/bert_text/results_v2.json`. Sweep wall
clock: 5,541.3 s (CPU, Mac).

Baseline for comparison: predicting "dead" for every held-out cell (the
majority class, 58.8% of the 3,584 held-out cells are dead) scores
**0.588** cells-correct — *higher* than every held-out run above.

## Observation: the model memorises, it does not learn to read the rule

This is a negative result, reported as such. Three of four runs reached
13/13 or 12/13 exact training rules (essentially perfect fit to the
training mixture, matching variant 1's exactness-on-512 result scaled up
to 13 rules). But held-out-rule accuracy never exceeded the trivial
majority-class baseline, and three of the four runs scored *below* it
(0.542, 0.459, 0.520 vs. 0.588). Held-out exact-rule rate was **0/7 in
every run**, for both named held-out rules (2x2, Maze) and all five random
held-out rules — a zero that held for the smallest and the largest
configuration tried.

Looking at one run's per-rule held-out breakdown (d=64, seed 1):

| held rule | rulestring | cells correct |
|---|---|---|
| 2x2 | B36/S125 | 0.439 |
| maze | B3/S12345 | 0.488 |
| rand_B157/S1347 | B157/S1347 | 0.615 |
| rand_B13458/S18 | B13458/S18 | 0.727 |
| rand_B3468/S1478 | B3468/S1478 | 0.500 |
| rand_B134/S0678 | B134/S0678 | 0.551 |
| rand_B14/S0135 | B14/S0135 | 0.533 |

No held-out rule reaches even 0.75, and several sit at or below chance for
a roughly-balanced binary task (0.439, 0.488, 0.500). There is no visible
correlation between a held-out rule's accuracy and its textual similarity
to a training rule (2x2 and Maze share digits with several training rules
but score among the *worst*).

**Reading this honestly**: a 2-layer, d=32-64 encoder, trained on 13
rule/text pairings with no explicit mechanism for compositional
generalisation (no structured way to combine "which digits are in the
Rule: string" with "how many of my neighbours are alive"), does what
transformers without an inductive bias for the task tend to do on a small,
discrete combinatorial space — it fits the training distribution
(near-perfectly) and does not generalise to combinatorially novel
rule/neighbourhood pairs. This does not mean a larger or differently
trained model couldn't learn the general mechanism (more training rules,
explicit birth/survive-digit attention supervision, or simply many more
than 13 training rules might close the gap) — only that *this* small
from-scratch encoder, trained this way, memorises per-rule mappings
instead. The question CONCEPT.md's "brute force with the right data" pole
poses — is a small encoder, aimed at the right data, or genuinely too small
to find general structure — is answered here, for this setup, as: with 13
training rules it is aimed only at the training rules, not the general
mechanism.

## Optional: CLS attention map (variant 1)

A d=16, layers=1, heads=4 variant-1 model (trained to 100% train accuracy
in 100 steps, lr=2e-3) was probed on four hand-picked cases: all-dead,
a birth case (3 live neighbours, dead self), a survival case (2 live
neighbours, alive self), and an overcrowding case (4 live neighbours,
alive self). All four predictions were correct. The CLS token's
layer-1 attention weights (averaged over the 4 heads) concentrate on the
`1` digit tokens — the live-neighbour and live-self bits — rather than on
structural tokens like `Self`, `Next`, or the instruction sentence; the
all-dead case (no `1` tokens at all) instead spreads its small attention
mass across generic tokens (`/`, `one`, `cell`). Raw weights:
`pytorch/bert_text/attn_examples.json`.

## Files

- `pytorch/bert_text/prompts.py` — per-cell prompt text (copied format),
  outer-totalistic `Rule` (reimplemented from `crates/life/src/rule.rs`),
  512-case generation, training/held-out rule mixtures.
- `pytorch/bert_text/vocab.py` — Qwen tokenizer loading + vocabulary
  reduction to used-token-ids.
- `pytorch/bert_text/model.py` — from-scratch `BertText` encoder (manual
  multi-head attention, CLS classifier head), batching/padding.
- `pytorch/bert_text/train_v1.py` — variant 1 sweep, writes `results_v1.json`.
- `pytorch/bert_text/train_v2.py` — variant 2 training-mixture + held-out
  eval, writes `results_v2.json`.
- `pytorch/bert_text/attn_map.py` — optional CLS attention probe, writes
  `attn_examples.json`.

## Machine / environment

Mac, CPU only (no MPS used). Python venv at `venv/` in this worktree:
torch 2.14.1, tokenizers 0.23.2, numpy 2.5.3. Tokenizer and full-vocab-size
source: Qwen2.5-0.5B-Instruct's `tokenizer.json` and its `config.json`
(`vocab_size: 151936`), from the repo's models directory (`hf download`),
path passed via `QWEN_TOKENIZER_PATH`.
